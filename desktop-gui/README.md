# File Sync Engine Desktop GUI Scaffold

This is the first checked-in desktop GUI scaffold for the file synchronization engine. It intentionally locks the process boundary before the full Wails application is generated or packaged.

## Boundary contract

- The GUI and daemon are separate decoupled applications.
- The sync engine runs as a separate daemon process owned by service/tray/runtime controls, not by the frontend runtime.
- closing the GUI unloads only the GUI; sync work continues in the daemon/service process.
- All control uses the daemon's authenticated encrypted API.
- No daemon code is imported into this frontend scaffold.
- This scaffold does not launch or supervise the daemon directly; platform service/tray handoff code will own lifecycle in later slices.

## Current scaffold

- `package.json` records the Svelte/TypeScript/Wails-oriented frontend commands.
- `wails.json` records the native shell entrypoint, frontend build/watch commands, output binary name, and product metadata without running Wails during this scaffold slice.
- `src/lib/daemonApi.ts` contains a small decoupled API client wrapper using an explicit API base URL and API key.
- `src/lib/nativeShell.ts` defines the Wails/native bridge. The native shell bridge reads the packaged resource manifest and resource observations from the shell, verifies bundled engine resources before enabling lifecycle controls, and calls the encrypted daemon API lifecycle flow.
- `src/App.svelte` provides a minimal local-daemon connection form, status probe, and bundled-daemon lifecycle panel gated by native-shell bundle verification.
- `src/lib/bundledEngine.ts` records the first bundle manifest contract: the bundle manifest maps each OS/architecture to exactly one daemon executable and verifies the bundled executable name, version, and SHA-256 metadata before offering lifecycle controls.

## Bundled daemon lifecycle boundary

Lifecycle control is API-only through the authenticated encrypted daemon API. The GUI may validate the release-packaged daemon metadata and then call the daemon service-command endpoint, but it must not import daemon internals, run daemon code in-process, or bypass platform service/tray ownership. Runtime lifecycle controls must call `verifyBundledEngineResourceManifest` and refuse start/stop/restart/status controls when any packaged daemon binary is missing or has a mismatched checksum. The native shell supplies file-existence and SHA-256 observations; the frontend contract only decides whether lifecycle actions are enabled. The first contract intentionally keeps install/startup registration as later work while locking the safe bundle-verification and encrypted-control boundary.

## Engine resource packaging

`scripts/package-desktop-engine-resources.sh <version>` copies the six existing daemon release binaries into `desktop-gui/resources/engine/` using the resource layout expected by `src/lib/bundledEngine.ts`:

- `linux/amd64/fse`
- `linux/arm64/fse`
- `darwin/amd64/fse`
- `darwin/arm64/fse`
- `windows/amd64/fse.exe`
- `windows/arm64/fse.exe`

The script consumes already-built artifacts from `build/<version>/`; it does not build or install toolchains, run Wails, or launch the daemon. It writes a resource `manifest.json` plus `SHA256SUMS` so later GUI runtime and packaging slices can verify packaged daemon checksums before enabling lifecycle actions.

`development/desktop-wails-builder/Dockerfile` plus `scripts/build-desktop-wails-builder-image.sh` provide a project-owned isolated builder-image recipe for the next real Wails build attempt. The default image tag is `fse-desktop-wails-builder:debian12-wails2.10.2`; building/running it does not install build tooling on the Hermes host, and large image/cache state belongs under `/development` or the container runtime rather than the source tree. The Debian builder includes Go, Node/npm, Wails v2.10.2, Linux WebKit/GTK dependencies, and Windows cross-compiler dependencies. `development/desktop-wails-builder/Dockerfile.linux-arm64` is the native Linux ARM64 builder recipe for hosts/runtimes that can run `--platform linux/arm64`; build it with `FSE_DESKTOP_WAILS_BUILDER_DOCKERFILE=development/desktop-wails-builder/Dockerfile.linux-arm64 FSE_DESKTOP_WAILS_BUILDER_PLATFORM=linux/arm64 scripts/build-desktop-wails-builder-image.sh fse-desktop-wails-builder:debian12-wails2.10.2-linux-arm64` and then point `FSE_DESKTOP_WAILS_BUILDER_IMAGE_LINUX_ARM64` at that image. `development/desktop-wails-builder/Dockerfile.linux-arm64-cross` is the amd64-host Linux ARM64 cross-builder layer; build it with `DOCKER_BUILDKIT=1 FSE_DESKTOP_CONTAINER_NETWORK=host FSE_DESKTOP_WAILS_BUILDER_DOCKERFILE=development/desktop-wails-builder/Dockerfile.linux-arm64-cross scripts/build-desktop-wails-builder-image.sh fse-desktop-wails-builder:debian12-wails2.10.2-linux-arm64-cross` and then point `FSE_DESKTOP_WAILS_BUILDER_IMAGE_LINUX_ARM64` at that cross-builder image when avoiding QEMU. `development/desktop-wails-builder/Dockerfile.linux-webkit40` and `development/desktop-wails-builder/Dockerfile.linux-arm64-cross-webkit40` provide the legacy WebKitGTK 4.0 compatibility builder lanes for older Linux installs; build them with `FSE_DESKTOP_WAILS_BUILDER_DOCKERFILE` and tags such as `fse-desktop-wails-builder:debian12-wails2.10.2-linux-webkit40` / `fse-desktop-wails-builder:debian12-wails2.10.2-linux-arm64-cross-webkit40`, then pass them with `FSE_DESKTOP_WAILS_BUILDER_IMAGE_LINUX_WEBKIT40` or target-specific overrides. `development/desktop-wails-builder/Dockerfile.windows-arm64-llvm-mingw` is the Windows ARM64 LLVM-MinGW builder layer; build it with `FSE_DESKTOP_WAILS_BUILDER_DOCKERFILE=development/desktop-wails-builder/Dockerfile.windows-arm64-llvm-mingw scripts/build-desktop-wails-builder-image.sh fse-desktop-wails-builder:debian12-wails2.10.2-windows-arm64-llvm-mingw` and then point `FSE_DESKTOP_WAILS_BUILDER_IMAGE_WINDOWS_ARM64` at that image. The build script performs a container DNS/network preflight against `deb.debian.org` before `docker build`/`podman build` so broken isolated-container networking fails quickly without leaving another failed build attempt; set `FSE_DESKTOP_SKIP_NETWORK_PREFLIGHT=1` only when intentionally testing the build despite that preflight. Set `FSE_DESKTOP_CONTAINER_NETWORK=host` (or another runtime-supported network mode) when the container runtime needs explicit network selection for the builder-image preflight/build or later Wails build containers.

`scripts/build-desktop-wails-darwin-builder-image.sh <sdk-tarball>` adds the Apple SDK/osxcross-capable isolated builder layer needed for real `darwin/amd64` and `darwin/arm64` Wails outputs. It consumes a legally obtained caller-supplied SDK tarball (or `FSE_MACOS_SDK_TARBALL`), stages it only under `/development/fse-desktop-wails-builder-cache/darwin-osxcross-context`, rewrites an unversioned `MacOSX.sdk/` archive root to a version-bearing `MacOSX<version>.sdk/` root so osxcross can infer and move the SDK correctly, builds `fse-desktop-wails-builder:debian12-wails2.10.2-darwin-osxcross`, and removes the temporary SDK copy afterward even if the container build fails. It accepts `FSE_DESKTOP_CONTAINER_NETWORK` (for example `host`) for the isolated Docker/Podman build so known container DNS failures can be corrected without installing tooling on the Hermes host. When using Docker, it enables BuildKit by default if `DOCKER_BUILDKIT` is not already set, avoiding this host's legacy Docker build path that can stall after creating trivial intermediate containers. The Darwin Dockerfile includes a narrow osxcross compatibility patch for macOS 26.x SDK patch releases such as the current 26.5 SDK so the build does not fail at the upstream `Unsupported SDK` guard. It does not commit or download Apple SDK contents and still does not install build tooling on the Hermes host; set `FSE_DESKTOP_WAILS_BUILDER_IMAGE=fse-desktop-wails-builder:debian12-wails2.10.2-darwin-osxcross` before `scripts/build-desktop-gui-wails.sh <version>` when producing Darwin outputs.

`scripts/check-desktop-darwin-readiness.sh <version>` is the Darwin readiness check for the remaining macOS artifact gate. It reports the legal Apple SDK tarball, osxcross builder image, Darwin Wails outputs, and all-six release packaging gate without installing host tooling. If `FSE_MACOS_SDK_TARBALL` is unset, it automatically checks the recurring-worker staging copy at `/development/apple-sdk/MacOSX.sdk.tar.xz` so a verified Syncthing handoff does not have to be re-exported in every cron environment. It also reports active Darwin builder status from `FSE_DESKTOP_DARWIN_BUILDER_STATUS` (default `/development/logs/file-sync-desktop-darwin/build-darwin-builder.status`) plus the tracked `pid`, stale/dead process state, and latest builder log progress line when available, so repeated worker passes can distinguish a moving running SDK-backed builder from a failed/stalled builder or missing local packaging inputs.

`scripts/build-desktop-gui-wails.sh <version>` runs Wails inside caller-supplied Docker/Podman builder images, mounts the repository read-only, copies the GUI source into container-local scratch space, and writes real Wails outputs under `desktop-gui/wails-output/<target>/` for all six desktop targets. If the Darwin Wails cross-compile path fails or produces no `build/bin`, the Darwin lane now falls back to a packageable macOS `.app` browser-shell bundle that embeds the built frontend `dist/` files, serves them from loopback with a pure-Go `CGO_ENABLED=0` helper, and opens the default browser; this keeps package artifacts unblocked while the full native Wails/macOS binding lane remains the preferred target. Set `FSE_DESKTOP_WAILS_BUILDER_IMAGE` as the default image and optionally override by OS (`FSE_DESKTOP_WAILS_BUILDER_IMAGE_LINUX`, `FSE_DESKTOP_WAILS_BUILDER_IMAGE_WINDOWS`, `FSE_DESKTOP_WAILS_BUILDER_IMAGE_DARWIN`) or exact target (`FSE_DESKTOP_WAILS_BUILDER_IMAGE_LINUX_AMD64`, `FSE_DESKTOP_WAILS_BUILDER_IMAGE_WINDOWS_ARM64`, `FSE_DESKTOP_WAILS_BUILDER_IMAGE_DARWIN_ARM64`, and the matching amd64/arm64 variants). The script verifies each selected image exists locally with `docker/podman image inspect`, then runs a cheap target-toolchain preflight for required commands such as Go, npm, Wails, `aarch64-linux-gnu-gcc`, `x86_64-w64-mingw32-gcc`, and Darwin osxcross compilers before it deletes/recreates a target output directory or starts the expensive frontend/Wails build. When `FSE_DESKTOP_DISABLE_CONTAINER_AUTO_RM=1` is set for Docker daemons that hang during automatic removal, the script uses an explicit create/start/wait lifecycle for both preflight and build containers so output remains observable and exited containers are left for manual cleanup. Linux builds default to `FSE_DESKTOP_LINUX_WEBKIT_API=4.1`, which maps to Wails `webkit2_41`, because Ubuntu 24.04+/newer distros no longer ship WebKitGTK 4.0 runtime packages. For older distro lanes, `FSE_DESKTOP_LINUX_WEBKIT_API=4.0` maps to Wails `webkit2_40`. WebKitGTK 4.0 and 4.1 are separate ABI/pkg-config lanes, so package metadata must match the lane used to build the binary instead of pretending a differently named WebKit package can satisfy the dynamic linker. `scripts/build-package-desktop-linux-webkit-variants.sh <version>` is the release handoff for shipping both lanes: it writes `desktop-gui/wails-output-webkit41/` and `desktop-gui/wails-output-webkit40/`, then packages `build/<version>/desktop-gui/linux-installers-webkit41/` and `build/<version>/desktop-gui/linux-installers-webkit40/`. Darwin builds now explicitly export `CC`/`CXX` as `o64-clang`/`o64-clang++` for `darwin/amd64` and `oa64-clang`/`oa64-clang++` for `darwin/arm64`, so Wails uses the osxcross compiler that the selected SDK-backed builder image preflight verified. It also reads image architecture through `docker/podman image inspect` instead of starting a target container just to identify architecture, and refuses to run the native Linux ARM64 builder through CPU emulation on a non-ARM64 host unless `FSE_DESKTOP_ALLOW_EMULATED_TARGET_RUN=1` is set deliberately; use a native ARM64 isolated builder host or an amd64 cross-builder image for that target. It does not install build tooling on the Hermes host.

`scripts/package-desktop-gui-release.sh <version>` packages already-built Wails desktop outputs and verified engine resources into one zip per desktop target under `build/<version>/desktop-gui/`. It expects GUI bundles under `desktop-gui/wails-output/<target>/` (or an explicit output-root argument), including non-empty target executables at `fse-desktop` for Linux, `fse-desktop.exe` for Windows, and `fse-desktop.app/Contents/MacOS/fse-desktop` for macOS. It includes a `docs-snapshot`, writes release `SHA256SUMS`, and does not run Wails, npm, Go builds, or install toolchains. The packager now preflights every desktop target, required Wails executable, and bundled engine path before replacing the output directory, reporting all missing/empty inputs at once so a failed six-target handoff does not delete existing verified archives. `FSE_DESKTOP_GUI_RELEASE_TARGETS` can be set to a comma-separated explicit subset only for reviewable partial packaging of already-verified targets; final release packaging must leave it unset so all six targets are preflighted and packaged together. Use the isolated build script or `/development` to produce the Wails outputs first, then use this reviewable packaging handoff to assemble desktop release archives without mutating the Hermes host.

`scripts/package-desktop-linux-installers.sh <version>` produces `.deb`, `.rpm`, and `.AppImage` artifacts for `linux-amd64` and `linux-arm64` after real Wails Linux outputs and bundled engine resources already exist. It requires prebuilt Wails outputs and bundled engine resources, calls already-available `dpkg-deb`, `rpmbuild`, and `appimagetool`/`FSE_DESKTOP_APPIMAGETOOL` inside the caller's isolated packaging environment, writes checksummed artifacts under `build/<version>/desktop-gui/linux-installers/`, and does not run Wails/npm/Go builds or install packaging tools. Set `FSE_DESKTOP_LINUX_INSTALLER_TARGETS="linux-arm64"` or another supported subset when packaging one architecture inside a target-specific isolated environment. For cross-AppImage packaging, provide target runtime files with `FSE_DESKTOP_APPIMAGE_RUNTIME_AMD64` and/or `FSE_DESKTOP_APPIMAGE_RUNTIME_ARM64`; the script passes them through appimagetool `--runtime-file` so a non-host packaging environment can still embed the correct AppImage runtime. The package metadata and AppImage launcher keep the daemon independent from the GUI: service setup must use a service-owned extracted/copied daemon binary or an equivalent engine-only daemon path, while GUI launches connect through the authenticated API. `.deb` metadata defaults to `libgtk-3-0 | libgtk-3-0t64` plus the WebKitGTK package matching `FSE_DESKTOP_LINUX_WEBKIT_API`: `libwebkit2gtk-4.1-0` for 4.1 builds or `libwebkit2gtk-4.0-37` for 4.0 builds. This keeps GTK flexible across normal/t64 package-name transitions and avoids rejecting newer GTK 3 package revisions while still requiring the matching WebKitGTK ABI lane. Metadata can be overridden with `FSE_DESKTOP_DEB_DEPENDS`; `.rpm` metadata similarly defaults through `FSE_DESKTOP_RPM_REQUIRES`. AppImage engine-only mode is available with `--fse-engine-daemon` or `FSE_DESKTOP_APPIMAGE_ENGINE_MODE=1`; it executes the bundled Linux engine for the packaged architecture (override with `FSE_DESKTOP_APPIMAGE_ARCH` only for explicit extracted-layout testing) so service setup can start the daemon without keeping the GUI resident. The 0.1.36-dev pass produced and verified the complete Linux installer set under `build/0.1.36-dev/desktop-gui/linux-installers/`: amd64 and arm64 `.deb`, `.rpm`, and `.AppImage` artifacts plus `SHA256SUMS`.

## First-launch daemon registration

The desktop scaffold now includes the first-launch daemon registration flow. The native shell detects whether the bundled daemon is already registered for the current OS and reports that status to the frontend. When registration is required, the GUI asks whether to configure automatic startup/login/start-at-boot before requesting registration. Registration uses the encrypted service-command API after bundle verification; the frontend still does not install services directly, spawn processes, or embed secrets in generated service files. Native shell/platform code remains responsible for presenting reviewable OS-specific handoff details and persisting the final service state.

## GUI-owned non-service daemon launch/adoption

The native Wails shell now includes concrete GUI-owned non-service daemon launch/adoption. When no system/user service is installed or reachable, it starts the verified bundled daemon as a separate process (a separate non-service process) for the current user and returns a recorded session. That session persists a reconnectable session record and records PID/API/credential state (`pid`, encrypted API URL, credential reference, config/state paths, and session mode) so the GUI can reconnect later, adopt an already-running process, and stops it through the authenticated encrypted `/v1/stop` daemon API instead of in-process calls. The default `persistent-user-daemon` mode preserves daemon independence: closing the GUI does not silently kill sync. A `temporary-session-only` temporary/session-only mode is allowed to stop with the GUI only when the user explicitly chose it before the GUI may treat process lifetime as tied to the current session.

## OS startup/login and tray integration contract

The scaffold now records the OS startup/login and tray integration contract without implementing platform-specific tray code in the frontend. The daemon/service owns the tray icon/status, and the native shell reports daemon-owned tray state plus startup integration state to the GUI. double-clicking the daemon tray icon opens or focuses the separate GUI app, while the GUI remains independent and unloadable after use. The frontend only calls bridge methods such as `getDaemonTrayStatus`, `getDaemonStartupIntegrationStatus`, and `openGuiFromDaemonTray`; platform code remains responsible for Windows/macOS/Linux tray APIs and startup registration.

The Windows startup/tray bridge now has a concrete reviewable contract in `src/lib/windowsStartupTray.ts`: it forces lifecycle status requests through `controlVerifiedBundledDaemonLifecycle` with `platform: 'windows'`, reports Service Control Manager ownership, renders a per-user `fse-desktop://open` protocol-registration PowerShell handoff, and uses `Start-Process 'fse-desktop://open'` as the tray-open command. It deliberately keeps the no direct daemon process launch boundary; the Windows shell/tray host executes platform-owned handoff text and opens/focuses the separate GUI instead of importing or launching daemon internals from the frontend.

The macOS startup/tray bridge now has a concrete reviewable contract in `src/lib/macosStartupTray.ts`: it forces lifecycle status requests through `controlVerifiedBundledDaemonLifecycle` with `platform: 'launchd'`, reports LaunchAgent/LaunchDaemon ownership, renders `fse-desktop://open` URL-scheme registration guidance for the separate GUI app, and uses `open 'fse-desktop://open'` as the menu-bar tray-open command. It keeps the daemon/service-owned menu bar status item and no direct daemon process launch boundary; macOS shell/tray code owns LaunchServices/menu-bar integration while the frontend stays unloadable.

The Linux startup/tray bridge now has a concrete reviewable contract in `src/lib/linuxStartupTray.ts`: it forces lifecycle status requests through `controlVerifiedBundledDaemonLifecycle` with `platform: 'systemd'`, reports systemd user/system service ownership, renders an XDG desktop-entry/URI-handler registration handoff for `fse-desktop://open`, and uses `xdg-open 'fse-desktop://open'` as the StatusNotifier/AppIndicator tray-open command. It keeps the daemon/service-owned tray/status boundary and no direct daemon process launch.

The daemon tray double-click handoff now has a focused frontend/native-shell contract in `src/lib/trayOpen.ts`. It receives `fse-desktop://open` or `--open-from-tray` from the platform tray handoff; the GUI then calls `showMainWindowFromDaemonTray`, which focuses or shows the already separate GUI process. This path does not launch the daemon, import daemon internals, or require the GUI to stay resident after use.

## Local engine controls panel

The scaffold now includes a Local engine controls panel backed by `src/lib/daemonApi.ts`. The panel can read redacted config and send peer, folder, discovery, transfer, maintenance scrub, web GUI, and non-secret config commands through the daemon API, so ordinary local management has no manual config-file editing or command-line switches. The latest pass replaces the first representative buttons with validated local engine forms that validate peer IDs, folder IDs, paths, discovery options, transfer scopes, maintenance scope, web GUI actions, and non-secret config patches before sending API requests. The panel now presents per-area operation status for peer, folder, discovery, transfer, maintenance, web GUI, and config controls, including accepted, pending, failed, and completed states so users do not have to read raw JSON to see whether a local engine action is still waiting, failed validation/API execution, or completed after a status refresh.

API certificate trust controls are now part of the selected-host daemon settings view. The GUI can fetch the active certificate fingerprint through `/v1/api/trust`, show whether `trustedCertificateMatches` is true, and pin the active certificate through `/v1/api/trust-command` after the user verifies the TOFU pairing context. The control displays certificate fingerprints and match status only; it does not expose API keys, TLS private-key material, or secret-bearing config fields.

The scaffold now uses a host-scoped information architecture instead of a single long page. A left-side host/sidebar shell pins the local host first and exposes dedicated views for overview, folders, peers, transfers, warnings/logs, maintenance/backups, daemon settings, desktop app settings, and help/details. The existing local engine control forms are scoped to the daemon settings view for the selected host, while overview keeps connection, startup/tray, and bundled lifecycle status together. The settings/help slice now splits a dedicated selected-host daemon settings page from a separate desktop GUI settings menu and dedicated help/details pages, so daemon identity/API/folder/peer/discovery/metadata/logging/backup policy, GUI-only theme/window/credential/notification preferences, and explanatory encryption/pairing/maintenance/repair/backup details each have distinct homes.

The desktop GUI now has a first multi-instance instance registry contract in `src/lib/instanceRegistry.ts`. The local instance pinned first entry always represents the bundled engine and opens by default; remote daemon API endpoints are stored as endpoint metadata plus a credential reference, not raw API keys. The sidebar groups Local bundled engine and Remote daemon instances, and selected host scope is explicit so folders, peers, transfers, warnings, settings, and maintenance actions cannot accidentally apply to the wrong daemon. The latest slice turns that registry into an expandable left navigation panel with per-group collapse/expand controls, readable connection state chips, a readable host status layout for online/offline state, remaining receive/send data, and average receive/send rates, and quick switching that updates the selected host API URL without storing secrets. The host list now also shows clear pairing/negotiation status for identity-linked peers, covering discovered, connecting, negotiating identity, exchanging keys, waiting on relay/mesh hop, direct connection established, paired, failed, revoked identity, and offline states while progressive discovery hydrates details. The selected-host whole-interface scope is now visible as a banner above every operational view: every operational view uses the selected managed daemon instance for labels, endpoint context, settings, folders, peers, transfers, warnings, and maintenance, while only the top GUI menu remains desktop-app scoped. The secure credential storage contract is represented by `src/lib/credentialVault.ts` and native-shell bridge methods: Windows uses Windows Credential Manager, macOS uses macOS Keychain, and Linux uses Freedesktop Secret Service, keeping remote API credentials out of the registry and frontend storage. The Peers & identity view now includes remote instance onboarding for API endpoint/key, pasted pairing code, imported identity file, scanned animated code, or loaded shared identity sources; raw API keys stay in native credential storage, can automatically populate reachable same-identity instances from a loaded shared identity, newly discovered same-identity peers appear from only a unique peer ID/code, and progressively fills in name, status, capabilities, folders, rates, and other metadata as negotiation continues.

The first remote-management mesh contract is now documented and scaffolded in `src/lib/instanceRegistry.ts` and the Peers & identity view. It treats the remote management plane as a trusted eventually-consistent mesh where each node owns exactly one canonical settings document, remote edits are stored as durable per-target pending command records, and the config file as a local import/export surface is reconciled into the owning node's document instead of overwriting other nodes. The daemon now persists per-node settings documents in JSON and Badger metadata stores and exposes a read-only authenticated `/v1/mesh/settings` API with optional `nodeId` filtering; documents are owner-key validated and redacted before daemon API exposure so cached peer settings cannot be applied to the wrong node or leak secret-looking fields. The Peers & identity view can now refresh remote mesh document status for online, relay-reachable, and offline instances, queue a non-secret selected-host settings patch through `/v1/mesh/settings-command`, and show pending remote settings changes with queued/applied/failed/acknowledged state instead of requiring raw JSON inspection. Offline selected-host edits are modeled as local durable pending changes until the owner node receives, validates, applies, and acknowledges them. This keeps the core promise that offline instances can be inspected or queued for later adoption through reachable identity peers while keeping patches non-secret, idempotent, authenticated, and owner-applied when the target reconnects.

The folders view now includes live remote folder-tree browsing through the selected remote host's authenticated API. The browse helper only lists directories for folder-picker safety, disables live browse buttons when the selected host is offline or unreachable, and keeps manual path entry available so an unreachable selected host does not block configuring or pasting a known path; manual path entry remains available when offline.


The Peers & identity view now has the first identity pairing export/import presentation scaffold. It can request a daemon-generated identity package over the authenticated encrypted API, show it as copyable text, offer the same payload as a downloadable identity file, parse a pasted or uploaded identity file for import readiness, and run daemon-owned import execution through `/v1/identity-import` so the frontend never turns bootstrap proof material into traffic keys itself. It now builds a QR code fallback payload as a data URL and a desktop QR fallback image rendering checkpoint for a native/browser QR renderer, keeping that secret-bearing QR fallback image shown only in the pairing view rather than logs/status. It also includes an animated visual pairing frame contract and generated frame list: payloads are split into privacy-preserving animated pairing fragments carrying `sessionId`, `frameIndex`, `frameCount`, `payloadSha256`, `payloadByteLength`, and `frameKind`; each displayed shard is a recoverable linear mix instead of a raw contiguous payload chunk, so a single captured frame cannot reveal much of the identity code. The frame set adds roughly 30% total-frame parity so assembly can recover missing data frames before checksum verification and daemon-owned import. The animated code uses conservative animated pairing density: 64 bytes per frame, `large-camera-friendly` visual modules, and slower frame timing for weak cameras and shaky hands until empirical scanner testing proves a denser profile reliable. The scanner progress contract will keep scanning subsequent animation loops, de-duplicate already-seen frames, and show `Keep phone pointed at screen until pairing is complete.` while collecting missing/new frames instead of failing after the first incomplete pass. The desktop animated pairing camera scanner now has a UI-shell contract for camera permission, decoded/rejected frame counts, progress percent, missing frames, and `Keep camera pointed at the animated code until pairing is complete.` guidance, with complete-payload verification before daemon-owned import. Pairing payloads are treated as secret identity material and are not routed through logs/status.
