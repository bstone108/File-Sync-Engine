# Mobile GUI Architecture

This document captures the first mobile GUI packaging and runtime stance for the file synchronization engine. It is a contract for the first Android and iOS slices, not a claim that the mobile apps are already implemented.

## Shared mobile stance

- The mobile apps manage a local engine where the platform allows it and manage remote daemons through the same authenticated local encrypted API / remote encrypted API contract used by the desktop GUI.
- The GUI and sync engine stay logically separated: UI screens call daemon/API capabilities instead of importing daemon internals.
- Remote instance management must match the desktop model: local instance first when present, arbitrary remote daemon endpoints, pairing-based onboarding, status/warnings/transfers/settings views, and eventual identity mesh relay for unreachable instances. Mobile remote instance onboarding supports direct API endpoint/key, pasted pairing code, uploaded identity file, scanned animated pairing code, and shared identity file import, while keeping Android Keystore / iOS Keychain as the only place for raw credentials.
- Secrets are kept in platform secure identity/key storage. The app registry stores credential references and redacted metadata only; bearer credentials stay out of ordinary app preferences/files. Loaded shared identity snapshots can perform automatic same-identity instance population before full details are known, and the host entries progressively hydrates status, folders, capabilities, and rates as identity negotiation completes.
- Identity pairing import/export must support copyable text, downloadable/shareable identity files, pasted/imported files, QR fallback payloads, platform share-sheet export, uploaded identity files, shared identity files, and animated pairing code scanning with progress, frame de-duplication/reordering, complete-payload verification, daemon-owned encrypted import execution, and secure local storage after import.
- Android identity import stores accepted pairing material through Android Keystore-backed secure storage; iOS stores accepted pairing material through iOS Keychain-backed secure storage. App-local registries may keep only redacted identifiers, readiness/progress state, and credential references.
- Mobile network policy must be explicit. A user setting can disable sync on cellular networks, and the app must enforce it through platform network capability/state checks before starting transfer work.
- Permission requests must be derived from configured sync options. Android and iOS clients should present storage/network/location/notification/background permissions only when the enabled local sync, discovery, background work, notification, or network-policy features require them, including location permission when required to detect Wi-Fi/network state.
- When platform policy, power state, permissions, background limits, network policy, or OS settings restrict work, the UI reports degraded sync status instead of pretending continuous daemon behavior is available.
- The first mobile daemon API client is a shared TypeScript contract for folders, peers, discovery, transfers, warnings/logs, maintenance, backups, and settings. It uses credential references only in mobile state; platform secure storage resolves API keys at call time for authenticated encrypted API requests.
- Mobile identity-linked mesh relay is a shared contract for remote management when a selected instance is offline or not directly reachable. Direct encrypted API remains preferred; identity mesh relay can carry cached settings/status inspection and durable pending settings changes through reachable peers; fully offline edits stay queued until a route appears. Delivery is eventually consistent and must show pending/applied/failed/acknowledged status after owner-side authentication, authorization, validation, and acknowledgement.

## Android approach

- Package the Android app with a bundled daemon binary/library shape appropriate for Android targets once the daemon build target exists. The daemon state root stays app-owned and is exposed to the UI only through the local encrypted API.
- Run active local sync using an Android foreground service for user-visible long-running work, with an ongoing notification and explicit stop/pause controls.
- Use WorkManager for deferred/retryable background tasks such as metadata catch-up, checkpoint flushes, small pending transfers, scrub/repair checks, and retry after connectivity returns.
- Request storage, network, notification, and background-related permissions based on enabled features. Request battery optimization exemption only when continuous/background sync is enabled, explain why, and surface degraded sync status if the OS or user declines.
- Honor metered/cellular restrictions, roaming state, charging/battery conditions, and user pause/cancel commands before scheduling work.
- Keep Android pairing/import secrets in Android Keystore or another platform-secure credential facility; app-local files may contain only redacted registry state and non-secret metadata.

## iOS approach

- Treat iOS as a policy-constrained mobile client first. A local bundled daemon may be possible only within documented App Store/platform limits; when continuous local background sync is not available, the app remains a strong remote-management and opportunistic-sync client.
- Use documented wake/work opportunities: iOS background tasks, background app refresh, background URLSession, silent push where allowed, notifications, and scheduled refresh. Do not depend on forbidden or non-public behavior.
- Design all iOS sync work for short wake windows: prioritize metadata catch-up, small pending transfers, resumable block chunks, durable checkpoints, quick exit, and rescheduling the next permitted wake before suspension.
- Surface degraded sync status whenever iOS background refresh, notification permission, battery/data settings, Low Power Mode, network state, or app suspension prevents daemon-like continuous work.
- Store pairing identity material and API credentials in Keychain-backed secure identity/key storage. Local app state must remain redacted and recoverable from daemon/identity metadata.

Latest Android battery optimization exemption checkpoint: `mobile-gui/src/android/androidShell.ts` now defines the prompt contract for reliable background sync. It will request battery optimization exemption only when continuous/background sync is enabled, explain that Android may pause sync while the app is idle unless exemption is granted, use Android's ignore-battery-optimizations settings action as the reviewable native handoff, and surface degraded status if the OS refuses or the user declines.

## Explicit boundaries

- This document is not a completed mobile implementation.
- iOS support must stay within documented public platform rules and may be degraded compared with a desktop/server daemon.
- Mobile clients must not log pairing packages, API keys, private identity keys, or raw credential material.
- Mesh-relayed configuration writes require authenticated, authorized, audited, idempotent delivery with pending/applied/failed/acknowledged status before they are treated as complete.
