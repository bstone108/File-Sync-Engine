# Desktop GUI Architecture

This document locks the first desktop GUI stack and packaging approach for the file synchronization engine. It is a planning/contract slice, not a completed GUI implementation.

## Chosen stack

The desktop GUI should use **Wails + Svelte/TypeScript** as the first implementation stack.

Why this fit:

- Wails keeps the desktop shell in Go, matching the daemon/tooling language and reducing cross-language runtime glue.
- Svelte/TypeScript gives a small, maintainable UI layer for the richer control surface: folders, peers, transfers, warnings, maintenance, backups, pairing, logs, and settings.
- The GUI can be packaged per platform while the existing daemon remains a separate, scriptable binary.
- The web-style frontend can share UI concepts and typed API models with the later optional web GUI without forcing the daemon to embed a web UI in headless deployments.

## Process boundary

The GUI and sync daemon must remain separate decoupled applications even when distributed together, with the sync engine running as a **separate daemon process**.

- The GUI starts, stops, installs, and configures the daemon through OS service/tray helpers and the authenticated control API.
- The daemon continues independently after the GUI window is closed.
- Closing the GUI should unload the GUI from memory; synchronization must continue through the daemon/service process.
- GUI-to-daemon operations use the daemon's authenticated encrypted API, not in-process calls or shared mutable state.
- The GUI should never require users to hand-edit large config files for normal operations.

## Bundled engine layout

Each desktop package should include the matching **bundled engine binary** for its target OS/architecture. The GUI discovers that bundled daemon through a versioned app resource path, verifies the expected executable name/metadata, and uses the same command/control contracts as external managers:

1. first launch detects whether the bundled daemon is already installed/registered as a system/user service, or whether a compatible daemon is already reachable;
2. the user is asked whether to configure startup/login/start-at-boot behavior;
3. if no service is installed/reachable, the GUI can start the bundled daemon as a separate non-service process for the current user/session and then manage it through the same authenticated encrypted API;
4. install/start/stop/status flows reuse the service-manager handoff patterns already present in the CLI when a service is used, and use explicit PID/API/credential adoption state when the GUI spawned a non-service daemon;
5. runtime control uses the encrypted API and redacted command/status events;
6. GUI updates and daemon updates are versioned together but remain separable enough for diagnostics and headless operation.

A GUI-spawned daemon is still a real independent daemon process, not an in-process library call. Closing the GUI must not silently kill synchronization unless the user explicitly selected a temporary/session-only mode. Later GUI launches should reconnect to the already-running daemon when possible, whether it was started by a service manager, manually, or by the GUI.

### GUI-owned non-service daemon launch/adoption

Concrete GUI-owned non-service daemon bridge: when no service or compatible reachable daemon exists, the desktop native shell now launches the verified bundled daemon as a separate process (a separate non-service process) and returns a `GUIManagedNonServiceDaemonSession`. The bridge writes a persisted session record that records PID/API/credential state, config/state paths, encrypted API URL, credential reference, launch time, and whether the next GUI launch should reconnect. Persistent sessions default to daemon independence: closing the GUI does not silently kill sync. A temporary/session-only mode is allowed only when the user explicitly chooses that lifetime. Stop/restart/status still use the daemon's authenticated encrypted `/v1/stop` API and related control endpoints, and native shell code owns platform process creation details.

## Target package matrix

The desktop GUI build/release flow must produce real working packages for every desktop OS/architecture target before the desktop GUI/client work can be considered complete:

- Windows amd64
- Windows arm64
- macOS amd64
- macOS arm64
- Linux amd64
- Linux arm64

Release artifacts should be unambiguous per OS/architecture, should include checksums, should support reproducible packaging handoffs, and should not require installing build tooling on the Hermes host. If extra GUI toolchains are needed, use `/development` or an isolated container/QEMU/chroot environment. Scaffolds, contracts, docs, and packaging scripts are not enough by themselves; the release must contain built GUI packages/artifacts that can actually run for each target.

**Current desktop artifacts are not test-ready until platform smoke evidence exists.** A successful CI build or package upload only proves packaging mechanics. Desktop stabilization must keep the artifacts classified as unproven until each relevant platform inventory records app launch, daemon launch/adoption, GUI-to-daemon API control, visible logs/errors, and first-use setup reaching a sync-ready state. The current known failure inventory must include the macOS ARM damaged-app launch check, Windows native desktop shell availability check, bundled daemon launch/adoption, GUI-to-daemon API control, and first-use setup reaches sync-ready state before any desktop package is called usable.

Linux has extra package requirements for each architecture:

- a `.deb` package;
- an `.rpm` package;
- an `.AppImage` package.

The Linux packages must preserve the primary daemon/GUI architecture. The sync daemon is the primary long-running component and must operate independently of the GUI. The GUI is an optional controller that connects to the daemon through the authenticated encrypted API. For AppImage-based setup, system/service installation must either extract/copy the daemon binary out of the AppImage into a normal service-owned location, or the AppImage must support an engine-only command-line mode that can run the daemon while later GUI launches connect to the already-running daemon.

Desktop GUI release packaging now has a reviewable script, `scripts/package-desktop-gui-release.sh <version>`, for the handoff after platform-specific GUI builds already exist. It packages already-built Wails desktop outputs plus the verified engine resources, includes a docs snapshot, writes `SHA256SUMS`, and deliberately does not run Wails/npm/Go builds. Windows targets produce both a zip package and an actual NSIS installer `.exe`; the zip is not treated as the installer. Other desktop targets produce one reviewable zip per target under `build/<version>/desktop-gui/`. The packager preflights every desktop target, required non-empty Wails executable (`fse-desktop`, `fse-desktop.exe`, or `fse-desktop.app/Contents/MacOS/fse-desktop`), bundled engine path, and `makensis` for Windows installer targets before replacing the output directory. For reviewable partial packaging of already-verified targets, `FSE_DESKTOP_GUI_RELEASE_TARGETS` may name an explicit comma-separated subset; final release packaging must leave it unset so all six target archives/installers are produced together.

Linux installer packaging handoff now has a dedicated reviewable script, `scripts/package-desktop-linux-installers.sh <version>`, for the Linux post-build step after real Wails Linux outputs and bundled engine resources already exist. It produces `.deb`, `.rpm`, and `.AppImage` artifacts for linux-amd64 and linux-arm64 under `build/<version>/desktop-gui/linux-installers/` with checksums, requires packaging tools to already exist in the isolated packaging image/environment, and deliberately does not install host tooling or run Wails/npm/Go builds. `FSE_DESKTOP_LINUX_INSTALLER_TARGETS` can restrict a run to one supported target for architecture-specific isolated packaging, and `FSE_DESKTOP_APPIMAGE_RUNTIME_AMD64` / `FSE_DESKTOP_APPIMAGE_RUNTIME_ARM64` let a caller supply target AppImage runtime files that are passed to appimagetool with `--runtime-file` when non-host packaging would otherwise embed the wrong runtime. The Linux package launcher and desktop metadata keep the daemon independently service-owned: service setup must extract/copy the bundled daemon into a normal service-owned location or use an engine-only daemon path, while GUI starts only the separate controller and connects through the authenticated API. `.deb` metadata defaults to `libgtk-3-0 | libgtk-3-0t64` plus the WebKitGTK package matching `FSE_DESKTOP_LINUX_WEBKIT_API`: `libwebkit2gtk-4.1-0` for 4.1 builds or `libwebkit2gtk-4.0-37` for 4.0 builds, and may be overridden by `FSE_DESKTOP_DEB_DEPENDS`; `.rpm` dependency metadata similarly uses `FSE_DESKTOP_RPM_REQUIRES`. AppImage engine-only daemon mode is implemented as `--fse-engine-daemon` or `FSE_DESKTOP_APPIMAGE_ENGINE_MODE=1`, executing the packaged Linux engine without launching the GUI so service setup can run the daemon independently and later GUI launches can adopt/connect to it. The 0.1.36-dev pass consolidated and verified the complete Linux installer set under `build/0.1.36-dev/desktop-gui/linux-installers/`: amd64 and arm64 `.deb`, `.rpm`, and `.AppImage` artifacts with `SHA256SUMS`.

### Isolated Wails build handoff

`scripts/build-desktop-gui-wails.sh <version>` provides the isolated Wails build handoff before release packaging. It requires a default caller-supplied Wails/Node builder image through `FSE_DESKTOP_WAILS_BUILDER_IMAGE`, runs the build through Docker or Podman with a read-only source mount, copies `desktop-gui/` into container-local scratch space for dependency/build output, and writes per-target Wails results to `desktop-gui/wails-output/<target>/`. The handoff can select different isolated images by OS (`FSE_DESKTOP_WAILS_BUILDER_IMAGE_LINUX`, `FSE_DESKTOP_WAILS_BUILDER_IMAGE_WINDOWS`, `FSE_DESKTOP_WAILS_BUILDER_IMAGE_DARWIN`) or exact OS/architecture (`FSE_DESKTOP_WAILS_BUILDER_IMAGE_LINUX_AMD64`, `FSE_DESKTOP_WAILS_BUILDER_IMAGE_WINDOWS_ARM64`, `FSE_DESKTOP_WAILS_BUILDER_IMAGE_DARWIN_ARM64`, plus the sibling target overrides), checks each selected image with `docker/podman image inspect`, and now runs a target-toolchain preflight for Go/npm/Wails plus target compilers such as `aarch64-linux-gnu-gcc`, `x86_64-w64-mingw32-gcc`, and Darwin osxcross commands before deleting/recreating target outputs or starting npm/Wails work. `FSE_DESKTOP_DISABLE_CONTAINER_AUTO_RM=1` switches the handoff from one-shot `docker/podman run` to an explicit create/start/wait container lifecycle for preflight and build steps, preserving output visibility while leaving exited containers available for cleanup on hosts where automatic removal stalls. For Linux targets, the script defaults to `FSE_DESKTOP_LINUX_WEBKIT_API=4.1`, derives Wails `webkit2_41` tags, preflights `webkit2gtk-4.1`, and generates Linux binaries for the WebKitGTK 4.1 runtime available on Ubuntu 24.04+/newer distros instead of requiring removed `libwebkit2gtk-4.0-*` runtime packages. `FSE_DESKTOP_LINUX_WEBKIT_API=4.0` remains available for older distro lanes and derives Wails `webkit2_40` tags plus `webkit2gtk-4.0` preflight; package metadata must follow the selected WebKitGTK ABI lane because 4.0 and 4.1 have different pkg-config names and runtime SONAMEs. For Darwin targets, the script now explicitly passes the matching osxcross compiler pair into Wails (`o64-clang`/`o64-clang++` for amd64 and `oa64-clang`/`oa64-clang++` for arm64) after the preflight verifies those tools exist in the selected SDK-backed image. The script also uses image-inspect metadata for image architecture checks and refuses native Linux ARM64 target containers on non-ARM64 hosts unless `FSE_DESKTOP_ALLOW_EMULATED_TARGET_RUN=1` is explicitly set, because the QEMU-emulated Node/Wails path can hang for longer than a normal worker pass. This keeps Node/npm/Wails/platform SDK installation outside the Hermes host while giving the release packager real Wails output directories to consume.

The first project-owned builder-image recipe is now checked in at `development/desktop-wails-builder/Dockerfile` with `scripts/build-desktop-wails-builder-image.sh` as the reviewable build command. Its default image tag is `fse-desktop-wails-builder:debian12-wails2.10.2`, and it does not install build tooling on the Hermes host; image/cache state belongs under `/development` or the container runtime. The recipe includes Go, Node/npm, Wails v2.10.2, Linux WebKit/GTK dependencies, and Windows cross-compilers. `development/desktop-wails-builder/Dockerfile.linux-arm64-cross` is the amd64-host Linux ARM64 cross-builder layer with ARM64 GTK/WebKit development packages and `aarch64-linux-gnu-*` compilers; build it with `DOCKER_BUILDKIT=1 FSE_DESKTOP_CONTAINER_NETWORK=host FSE_DESKTOP_WAILS_BUILDER_DOCKERFILE=development/desktop-wails-builder/Dockerfile.linux-arm64-cross scripts/build-desktop-wails-builder-image.sh fse-desktop-wails-builder:debian12-wails2.10.2-linux-arm64-cross` and use `FSE_DESKTOP_WAILS_BUILDER_IMAGE_LINUX_ARM64=fse-desktop-wails-builder:debian12-wails2.10.2-linux-arm64-cross` to avoid QEMU for Linux ARM64 Wails output. `development/desktop-wails-builder/Dockerfile.linux-webkit40` and `development/desktop-wails-builder/Dockerfile.linux-arm64-cross-webkit40` are the legacy WebKitGTK 4.0 builder lanes for older distros; tag them as `fse-desktop-wails-builder:debian12-wails2.10.2-linux-webkit40` and `fse-desktop-wails-builder:debian12-wails2.10.2-linux-arm64-cross-webkit40`, then pass them through `FSE_DESKTOP_WAILS_BUILDER_IMAGE_LINUX_WEBKIT40` / target overrides when producing the 4.0 compatibility packages. `development/desktop-wails-builder/Dockerfile.windows-arm64-llvm-mingw` is the Windows ARM64 LLVM-MinGW builder layer, selected with tag `fse-desktop-wails-builder:debian12-wails2.10.2-windows-arm64-llvm-mingw` and `FSE_DESKTOP_WAILS_BUILDER_IMAGE_WINDOWS_ARM64`, so the ARM64 target can use `aarch64-w64-mingw32-gcc` without host tooling. The build command now performs a container DNS/network preflight against `deb.debian.org` before invoking the isolated image build so broken Docker/Podman networking fails fast without another long failed `apt-get` layer; `FSE_DESKTOP_SKIP_NETWORK_PREFLIGHT=1` is available only for deliberate override attempts. `FSE_DESKTOP_CONTAINER_NETWORK` may be set to a runtime network mode such as `host` for both the builder-image preflight/build and the later Wails build containers when the isolated container runtime needs explicit network selection.

`scripts/build-desktop-wails-darwin-builder-image.sh <sdk-tarball>` supplies the Apple SDK/osxcross-capable isolated builder layer for Darwin targets. It requires a caller-provided SDK tarball (or `FSE_MACOS_SDK_TARBALL`), stages it only in `/development/fse-desktop-wails-builder-cache/darwin-osxcross-context`, rewrites an unversioned `MacOSX.sdk/` archive root to a version-bearing `MacOSX<version>.sdk/` root so osxcross can infer and move the SDK correctly, builds `fse-desktop-wails-builder:debian12-wails2.10.2-darwin-osxcross`, and removes the temporary SDK copy after the container build or build failure. Set `FSE_DESKTOP_CONTAINER_NETWORK` (for example `host`) when the isolated Darwin builder image needs explicit Docker/Podman network selection to avoid container DNS failures. When Docker is the selected runtime, the script enables BuildKit by default if `DOCKER_BUILDKIT` is unset so the Darwin layer avoids this host's legacy Docker build path that can stall after creating intermediate containers. The Dockerfile carries a narrow osxcross build-script patch so newly supplied macOS 26.x SDK patch releases such as Brandon's 26.5 SDK follow the existing Darwin 25-family path instead of failing early as `Unsupported SDK`. This layer does not commit or download Apple SDK contents, keeps SDK/tooling setup outside the Hermes host, and is the selected darwin builder image for later real `darwin/amd64` and `darwin/arm64` Wails output attempts.

`scripts/check-desktop-darwin-readiness.sh <version>` is the Darwin readiness check for the remaining macOS artifact gate. It reports the legal Apple SDK tarball, osxcross builder image, Darwin Wails outputs, and all-six release packaging gate without installing host tooling. If `FSE_MACOS_SDK_TARBALL` is unset, it automatically checks the recurring-worker staging copy at `/development/apple-sdk/MacOSX.sdk.tar.xz` so a verified Syncthing handoff does not have to be re-exported in every cron environment. It also reports active Darwin builder status from `FSE_DESKTOP_DARWIN_BUILDER_STATUS` (default `/development/logs/file-sync-desktop-darwin/build-darwin-builder.status`) plus the tracked `pid`, stale/dead process state, and latest builder log progress line when available, so cron passes can quickly prove whether an SDK-backed builder is still moving, failed/stalled, whether the output set is still missing, or whether final packaging can run.

The native Wails shell source now exists as a concrete build entrypoint: `desktop-gui/go.mod` pins the Wails v2 app module, `desktop-gui/main.go` embeds frontend `dist/` assets through Wails' asset server and binds the app bridge, and `desktop-gui/app.go` exposes a minimal runtime-info bridge that keeps the separate daemon/authenticated encrypted API boundary explicit. For Darwin only, the isolated build script has a packageability fallback for current osxcross/Wails failures: if the native Wails cross-compile fails or produces no `build/bin`, it copies the built frontend `dist/` into a macOS `.app` bundle and builds a pure-Go `CGO_ENABLED=0` loopback browser-shell launcher for `darwin/amd64` or `darwin/arm64`. That fallback keeps macOS package inputs unblocked without downloading or committing SDK contents, but the full native Wails app remains the preferred final runtime lane. Real six-target Wails outputs still require a separate isolated Wails/Node builder image to be available before the release packager can create the final desktop zips.

## Tray and startup integration

The app needs native tray behavior plus startup/login/start-at-boot setup, but platform ownership stays explicit:

- Windows: Start Menu/installer integration plus Service Control Manager handoff for the daemon where appropriate.
- macOS: LaunchAgent/LaunchDaemon handoff for daemon lifecycle and a native menu-bar/tray status item.
- Linux: systemd user/system service handoff and desktop-environment tray/status support where available.

The tray/menu status should be backed by daemon API state. Double-clicking the daemon tray icon should open or focus the separate GUI application. If the GUI exits, the tray/daemon state continues to be owned by the daemon/service side. The current daemon tray double-click handoff is represented by a frontend/native-shell bridge: platform tray code invokes `fse-desktop://open` or `--open-from-tray`, and the GUI shell uses `showMainWindowFromDaemonTray` to focus/show the separate GUI window without launching daemon internals.

## Information architecture starting point

The first GUI should avoid a one-page control pile. Use a host-scoped layout with dedicated areas for:

- overview/status;
- folders and sync groups;
- peers, discovery, identity pairing, and remote instances;
- transfers and queue state;
- warnings, logs, and events;
- maintenance, scrub, repair, and backup/snapshot operations;
- daemon settings for the selected host;
- desktop-app settings for GUI-only preferences;
- help/details pages that explain advanced options without cluttering normal operation.

The first remote-management mesh contract now treats the desktop remote-control plane as a trusted eventually-consistent mesh where each node owns exactly one canonical settings document. GUI/API edits become durable per-target pending command records, and the config file as a local import/export surface is reconciled into the owning node document instead of overwriting another node's settings. The daemon persistence/API foundation now covers both read-side settings documents and pending-change queueing/delivery/application: non-secret `/v1/config` patches update the local node's durable settings document with `source: "local-config"`, stream peers request `mesh_settings_changes`, owners validate/apply delivered changes idempotently, and targets send `mesh_settings_ack` results so the origin persists `acked` or `failed` status with update/error details for later GUI progress views. Local API queueing now rejects spoofed `originNodeId` values that do not match the authenticated daemon node, owner-side apply can enforce a per-document `mesh.authorizedSettingsPeers` allow-list before accepting a remote settings change, each pending settings change now retains a compact non-secret audit trail for queue/delivery/owner-apply/ack/failure transitions, and the routing layer has a non-mutating retry planner that keeps queued settings changes moving over reachable direct or trusted relay/mesh management paths until they are acknowledged, failed, not due yet, or past the configured attempt budget. JSON and Badger stores can save, load, and deterministically list owner-keyed per-node settings documents plus target-keyed pending settings changes with idempotency keys, owner/document or target/change mismatches fail closed, authenticated `GET /v1/mesh/settings?nodeId=<id>` exposes redacted cached documents for inspection without applying another node's config locally, and authenticated `POST /v1/mesh/settings-command` queues non-secret settings patches into durable per-target pending-change records without exposing patch keys or values in queue events. Stream peers can now request `mesh_settings_changes`, and the server delivers only queued pending changes addressed to the authenticated target peer, keeping other targets' changes and already-acknowledged records out of the response. Pulling peers can persist delivered changes locally and owner-apply them idempotently only when the target node ID matches the local node, updating that node's canonical settings document while marking the delivered change applied. A mesh-settings-only stream exchange can apply and acknowledge queued offline edits as soon as a node reconnects, without requiring a folder data transfer pass. The desktop scaffold now models offline selected-host edits as local durable pending changes until the owner node receives, validates, applies, and acknowledges them. This means offline instances can be inspected or queued for later adoption through reachable peers before owner-side validation/acknowledgement, while local and remote documents remain owner-scoped and non-secret.

The Folders view now supports live remote folder-tree browsing through the selected remote host's authenticated API. The GUI calls the daemon `/v1/filesystem/browse` endpoint for the selected host, receives directory entries only, and never shells out or reads the remote filesystem directly. Manual path entry remains available when offline, and the browse controls are disabled with an explicit offline/unreachable message so a disconnected host still allows typed or pasted roots without pretending the GUI can infer that host's filesystem paths; manual path entry remains available when offline.

The Peers & identity view now includes the first identity pairing export/import presentation scaffold. It requests daemon-generated packages only through the authenticated encrypted API, displays the package as copyable text, offers a downloadable identity file for save/share flows, validates a pasted or uploaded identity file, and runs daemon-owned import execution through `/v1/identity-import` so import planning/key preparation stays daemon-scoped and redacted.
